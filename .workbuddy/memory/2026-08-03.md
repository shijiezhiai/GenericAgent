
## 修复后台服务：微信 + 飞书启动失败（IM 通道）
- 现象：桌面 App 协作页把微信/飞书当后台服务拉起（ChannelManager.start → subprocess.Popen([sys.executable, frontends/wechatapp.py|fsapp.py])），均启动失败。

- 修复：①`pip install pycryptodome qrcode lark-oapi` 装进**两个** Python（app-support + bundle runtime），确保当前生效且升级重克隆不丢；②`bundle_build.py` CORE_DEPS 补这三行（根治，后续构建自带）。`websockets` 被 lark-oapi 从 16.1.1 拉到 15.0.1，无回归（App 代码不直 import websockets，仅用 uvicorn 间接依赖，兼容 15.x）。
- 验证：`python frontends/fsapp.py` 打印「飞书 Agent 已启动」并连上 wss://msg-frontier.feishu.cn；wechatapp 越过 import 进入启动（单独跑无内核才报 config Connection refused，属预期降级）。注意 `chatapp_common.py` 顶层 `from continue_cmd import ...` 要求 `frontends/` 在 path——以脚本方式 `python frontends/fsapp.py` 拉起时 Python 自动把脚本目录加入 sys.path，故正常；用 importlib 当模块导入会误报，非正式路径。
- 排查要点：先 `python -c "import frontends.xxx"` 复现 import 报错，再 `find_python()` 确认实际用的解释器，别只查系统 python。

## 2026-08-03 — 首响应延迟排查（停止按钮空转数十秒）
- 结论：**MCP server 串行冷启动**吃掉 99.4s（热缓存实测；冷缓存首跑 151.7s），占延迟 ~91%。前端轮询无锅（首轮 poll 0ms 延迟、稳态 500ms、退避仅 fetch 失败时触发）。
- 实测逐项（`McpClient(key,cfg).start()+list_tools()` 计时，8 个条目串行）：minimax-mcp / wenyan-mcp / redbook-search-comment-mcp **各 30.2s 超时且 tools=0**（合计 90.6s 纯浪费，因 `.mcp.json` 里 `${MINIMAX_API_KEY}` 等占位符未赋值，进程不响应 initialize，`mcp_client.py:208` timeout=30 硬编码只能死等）；lark-mcp 2.45s / playwright×3 各 1.0~2.25s / rss-reader 1.30s = 8.8s 有效。
- 链路：`app.js:8802 await POST /session/{id}/restore`（每次发送都调，`bridgeFetch` 无超时）→ `desktop_bridge.py:3111 restore_handler` **async def 里直接调同步 `restore_context`，卡死整个 aiohttp 事件循环**（这 99s 内 poll 等所有请求排队，故表现为"整个界面僵住"）→ `make_agent` → `GenericAgent.__init__`(agentmain.py:69-72) → `collect_mcp_tools()`(plugin_loader.py:761-782 朴素 for 循环，**无任何缓存**)。
- 次要：`_snapshot_cwd`(desktop_bridge.py:88-127) 对 ≤256KB 文件 `read_bytes()` 读全文，仓库根实测 772 文件/5.46MB/**144ms**，每轮跑 2 次（执行前后快照）。cwd=temp 时仅 0.5ms。
- 附带 bug（R5）：`agentmain.py:217-222` 每个 task 的 finally 都 `_c.stop()` 关掉全部 mcp_clients，但 `collect_mcp_tools()` 只在 `__init__` 调、`make_agent` 只在 `sess.agent is None` 时触发 → **花 99s 启动的 MCP 只有第一轮能用**，第二轮起进程已死但 schema 仍在工具列表里，模型调用会失败。
- 另：3 个插件(dev-enegine/content-create/long-running-agent)配了完全相同的 `npx @playwright/mcp@latest`，被当 3 个独立 server 各起一个进程，返回 24 个一模一样的工具；`@latest` 还导致每次访问 npm registry 解析版本。
- 方案（报告 `docs/perf_first_response_latency.md`）：P0-a 删 3 个坏 server（改配置零风险，99.4→8.8s）；P0-b `collect_mcp_tools` 用 ThreadPoolExecutor 并行 + 按 `(command,args)` 去重 + 握手超时 30→8s（→~2.5s）；P1-a MCP 懒加载（dispatch 到 `mcp__*` 时才起对应 server，schema 走磁盘缓存，→~0s）；P1-b `restore_handler` 改 `await asyncio.to_thread(...)`；P1-c 前端删冗余串行 `/restore`（`run_agent_turn:1863` 已负责建 agent）+ 给 `bridgeFetch` 加超时；P2-a 修 R5 生命周期；P2-b 快照首遍只记 (mtime_ns,size)、diff 后再回读变化文件。
- 排查手法可复用：写一次性探针脚本逐个 server 计时（放 temp/ 用完即删），**跑两次**区分冷缓存下包 vs 稳态耗时；判断是不是 MCP 的锅可临时把 `skills_config.json` 的 `plugin_dirs` 置空对比。
