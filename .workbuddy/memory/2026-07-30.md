## 修复：code_run/code_search/file_find 调用导致会话中断（2026-07-30 19:45）
- **现象**：在桌面 app 里一旦 agent 调用 `code_run`/`code_search`/`file_find` 等工具，会话就中断（网关收到非法 JSON-RPC）。
- **真因**：桌面内核 `frontends/kernel_server.py` 用 **stdio JSON-RPC**，其 `sys.stdout` 是协议管道（该文件已显式把 legacy bridge 的 stdout 重定向到日志以防污染，但工具侧没防）。
  - `ga.py` 的 `safe_print`（被 `self.print`/`myprint` 用作 code_run 流式输出、web_execute_js 结果、plan 模式、verbose prompt）**直接 `print()` 到 `sys.stdout`** → 把非协议字节写进 JSON-RPC 管道，网关解析失败→会话中断。
  - `code_run` 的 `subprocess.Popen` 与 `code_search/file_find` 的 `_run_rg`（`subprocess.run`）**未设 `stdin`** → 子进程继承内核的 **stdin（亦为 JSON-RPC 输入管道）**，存在干扰协议的风险。
- **修复**（`ga.py`，同步四处：源码 / `frontends/desktop/runtime/app/ga.py` / `~/Library/Application Support/GenericAgent/app/ga.py` / `/Applications/GenericAgent.app/.../runtime/app/ga.py`）：
  1. `safe_print` 改为 `print(..., file=sys.stderr)`（内核日志走 stderr，安全；CLI/桌面仍可见）。
  2. `code_run` 的 `Popen` 加 `stdin=subprocess.DEVNULL`。
  3. `_run_rg` 的 `subprocess.run` 加 `stdin=subprocess.DEVNULL`。
  - 四处均 `py_compile` 通过，已清对应 `ga*.pyc`。
- **生效**：需让 app 真正重启（Tauri 单实例 → 先 `pkill -9 -f GenericAgent; pkill -9 -f kernel_server; pkill -9 -f desktop_bridge`，再 `open /Applications/GenericAgent.app`；确认 `lsof -i :14168` 是新进程）。
- **经验（务必记）**：凡在 kernel_server(stdio JSON-RPC) 路径运行的代码，**绝不可写 `sys.stdout`**；流式输出只能走 `yield`（被 display queue 收集）或 `sys.stderr`。子进程统一 `stdin=DEVNULL` 以防继承协议管道。

## 会话中断仍未解决 → 内核级 stdout 保护（2026-07-30 19:55 续）
- **上一轮 ga.py 的 safe_print→stderr 修复后用户仍报中断**，说明污染源不止 `safe_print`，而是更宽泛的「裸 `print()` 污染管道」。
- **真正完整的污染源**：`llmcore.py`/`agentmain.py`/`ga.py` 里有大量**无 `file=` 的裸 `print()`**（`[Info] Load mykeys`、`[Cut]`、`[Debug] Current context`、`[LLM Retry]`、`[Cache]`、`[Output] tokens`、`Backend Error`、`User aborted the task.` 等）。这些跑在内核进程里，每次 LLM 调用/上下文压缩/重试/异常都会往 `sys.stdout`（JSON-RPC 管道）写非协议字节 → 网关解析失败→会话中断。普通对话不触发压缩/重试分支所以“看似正常”，一旦跑 code_run（产生长结果→触发压缩/重试）就炸。
- **彻底修复（内核级）**：改 `frontends/kernel_server.py`——在 `import desktop_bridge` 之前：
  - `_PROTOCOL_STDOUT = sys.stdout`（捕获真正的管道 fd，绝不写脏字节）。
  - 定义 `_StderrProxy(io.TextIOBase)`，把所有 `print()`（无 file=）重定向到 `sys.stderr`（内核日志流）。
  - `sys.stdout = _StderrProxy(...)`。
  - `_write()` 改用 `_PROTOCOL_STDOUT`（协议写盘只用真正管道 fd）。
  - 注意：`agentmain` 导入时 `sys.stdout.reconfigure(errors='replace')` —— proxy 提供 no-op `reconfigure` 兼容；`print(..., file=sys.stderr)` 显式写法仍走真实 stderr，不受影响。`web*` 等 IM 机器人里的 `file=sys.__stdout__`/`dup2` 不在内核路径，无需处理。
- **同步四处**：源码 `frontends/kernel_server.py` / `frontends/desktop/runtime/app/frontends/kernel_server.py` / `~/Library/Application Support/GenericAgent/app/frontends/kernel_server.py` / `/Applications/GenericAgent.app/Contents/Resources/runtime/app/frontends/kernel_server.py`。四处 `py_compile` 通过 + 清 `kernel_server*.pyc` + 重启 app（新 PID 3962）。
- **实测验证**（/tmp/kern_smoke.py，用 bundle 自带 python 跑）：
  - Test1：import 内核模块触发重定向后，裸 `print('TO_STDOUT_LEAK')` 不出现在 stdout、只进 stderr → 管道零泄漏。
  - Test2：直接拉起内核进程喂 `status` RPC，stdout 仅输出合法 JSON-RPC（`kernel.ready` 通知 + `status` 响应），无任何垃圾字节。
- **结论**：内核级保护后，任何模块的裸 print 都不会再污染管道；code_run/code_search/file_find 引发的会话中断应彻底消失。仍异常再查 fd 级直写（unlikely，IM 模块才用 `sys.__stdout__`/dup2）。
