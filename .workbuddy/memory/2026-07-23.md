### 中文搜索修复（IME 组合提交）
用户反馈 Ctrl+R 历史搜索只支持英文、不支持中文。根因：三处都从「单字符键事件」取查询，但中文走 IME 组合提交，不以单字符键形式出现。
- TUI：原判据 `len(event.key)==1 and isprintable()`，IME 提交时 `event.key=="ime"` 被过滤；改用 `event.is_printable and event.character`（与 Textual 原生 Input 一致，整段中文也能进）。
- Qt：`event.text()` 用 `len(text)==1` 限制挡掉整段中文（key()==Key_Unknown），且组合期空 text 被「其它键→取消」吞掉；改为接收任意可打印 `event.text()`（含多字符中文），`Key_Unknown` 且无 text 时仅吞掉不取消。
- JS：原 `e.key.length===1` 挡掉中文；IME 组合期 `e.isComposing` 直接 return 不收集，且中文提交只经 `compositionend` 派发（无监听）。改为：组合期（isComposing/key==='Process'）不拦截、不 preventDefault；新增 `inputEl` 的 `compositionend` 监听，把 `e.data`（整段中文）追加到查询。
三文件 `py_compile` / `node --check` 均通过。教训：凡是从键事件取"输入内容"的逻辑，必须同时处理 IME 组合提交（Textual 用 event.character、Qt 用 event.text + Key_Unknown、Web 用 compositionend）。

### 中文搜索修复（续）：拼音首字母混入查询 "d打"
用户实测：输入中文，查询变成「拼音首字母 + 中文」（如 打 → d打）。根因：IME 组合键被当普通可打印键——拼音字母（d）被追加进查询，随后中文（打）经 compositionend/inputMethodEvent 提交再追加，叠加成 d打。平台差异：WebKit/Safari/Tauri(WKWebView) 首字母按键 isComposing 可能为 false，但这类 IME 组合键统一带 **keyCode===229**（可选字符键）。
修复：
- JS：搜索态 keydown 跳过条件新增 `e.keyCode === 229`（与 isComposing / key==='Process' 并列），拼音字母不再进查询；中文仍由 `compositionend` 的 `e.data` 提交追加。
- Qt：新增 `QEvent.InputMethod` 处理（`_hs_ime_event`）：仅 `commitString()` 提交文本进查询，`preeditString()` 非空标记 `_hs_ime_composing`；`_hs_event` 中组合进行中（`_hs_ime_composing`）吞掉所有按键，且对 IME 提交后跟的 Key_Unknown 残留键用 `_hs_ime_just_committed` 去重；`_hs_start/_hs_accept/_hs_cancel` 重置 IME 标志避免卡死。
- TUI：终端 IME 由 OS 处理、只回传最终字节，无拼音逐键问题，未改。
三文件语法校验通过。教训：拦截 IME 不能只看 isComposing，WebKit 必须补 keyCode===229；Qt 不能靠 keyPress 取 IME 文本，要用 inputMethodEvent.commitString() 且组合阶段（preedit）吞掉按键。

## "project not found" 真正根因：项目名被双重 URL 编码
用户第二次报同样的错，诊断信息里的 `name` 是 `Flink%20Bug%20%E8%B7%9F...`（单层编码形态），证明浏览器发出的项目名被 **双重 URL 编码**（先 encodeURIComponent 一次，得到的 `%20` 等再被 encode 一次 → 服务端 aiohttp 只解码一层，剩余 `%20` 无法匹配目录）。
- 服务端实证：对 `/projects/<双重编码名>/library/.../preview` 发起请求，返回的 `name` 与用户报告完全一致 → 复现成功。
- 修复（两手都要硬）：
  1. 后端 `desktop_bridge.py`：`_resolve_project_dir` 与 preview/raw 两个 handler 在取 `match_info["name"]` 后先 `_unquote_name()`（urllib.parse.unquote 一次，try/except 包住）再校验/匹配。单层或双层编码都归一为解码名，命中真实目录（200）。仍保留 `/ \ ..` 等非法字符校验。
  2. 前端 `app.js`：新增 `encProject(name)`（先 `decodeURIComponent` 再 `encodeURIComponent`，try/catch 包住），把所有 `encodeURIComponent(phState.project)` / `encodeURIComponent(projectName)` 全部替换为 `encProject(...)`，覆盖 library/members/todos/datasources/assets 等所有项目 URL。无论 `phState.project` 处于解码/单层编码状态，结果都恰好单层编码，从源头杜绝双重编码。
- 验证：双重编码 preview/raw 现均 200；单层编码（正常路径）仍 200（无回归）；headless Chrome 加载无 JS 报错。
- `index.html` 缓存版本 app.js `321→322`。
- 教训：aiohttp 的 `match_info` 会解码一层路径段；凡前端 `encodeURIComponent(项目名)` 经浏览器发出后再被服务端解码，若中间多编码一次就会 404。统一用「先解后编」的归一化函数最稳。

## favicon 空白 bug 修复（Confluence 死链）
用户反馈：资料库网页条目「帮助文档-流计算任务开发」(url=https://info.bilibili.co/pages/viewpage.action?pageId=104988736) 及其子页面图标空白。
根因：原 `_resolve_favicon` 直接采信页面 `<link rel=icon>` 指向的 `/pages/static/images/favicon.ico`，但该链接是 Confluence 死链（302 跳登录页，非图片）；而真正可用的根目录 `/favicon.ico`（200 image/x-icon）反被忽略——解析逻辑从不验证候选是否真能返回图片。前端 `_applyLibFavicon` 的 onerror 用 `window.gaIcon('link')` 内联兜底，虽然 window.gaIcon 存在，但死链 302→HTML 时回退不稳定，表现为空白。
修复：
- 后端 `_resolve_favicon`：新增 `_verify_icon(session,url)`（GET 后查 status==200 且 Content-Type 含 `image/` 才有效，否则 None）；候选收集顺序 = link rel=icon > apple-touch > og:image > 根目录 `/favicon.ico`，去重后逐个 `_verify_icon`，第一个有效即返回并缓存；全失败 return None（→ 前端默认图标）。
- 前端 `_applyLibFavicon`：改为先 `var fallbackHtml = iconEl.innerHTML` 捕获默认图标，再用 `new Image()`，onload 时替换、onerror 时还原 `fallbackHtml`（不再依赖 `window.gaIcon` 内联）。
- `index.html` 缓存版本 app.js `323→324`。
验证：bilibili 页面现解析为 `https://info.bilibili.co/favicon.ico`（200 image/x-icon，可直接加载）；github/python.org/HN/zhihu 等回归正常；node --check 通过。需重启 bridge 生效。

## favicon 白色 SVG 不可见修复（微信文章条目）
现象：「FFA 2026 会场介绍」（mp.weixin.qq.com 文章）web 条目图标空白。
根因：该页 `<link rel=icon>` 指向纯白 SVG（fill="#FFF"，是微信品牌绿底上用的白 logo），后端 `_verify_icon` 只校验「200 + image/*」就通过并返回，白图标在浅色卡片上不可见。浏览器 tab 实际用的是绿色 /favicon.ico。
修复：desktop_bridge.py `_verify_icon` 对 svg content-type 额外读取 body，用新 helper `_svg_is_all_white(text)` 检测——收集所有 fill/stroke 显式颜色，若全是白色变体（#fff/#ffffff/white/rgb(255,255,255)）则判不可见返回 None，候选顺延。无显式颜色（默认黑）或含位图/其他色→视为可见。
结果：微信文章现解析到 res.wx.qq.com 的 .ico（绿色可见）；bilibili/github/知乎无回归。仅改后端，无需 bump 前端版本，用户硬刷新即可。
教训：favicon 校验不能只看 HTTP 200 + image/*，还要考虑「可见性」——纯白/透明图标在浅背景等于空白。
