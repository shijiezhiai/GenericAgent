## 新增 git_checkpoint 工具（对齐 Claude Code/Codex/Cursor）
- 需求：截图指出 GA 缺乏 Git 原生工作流（无结构化 git 操作、无法直接出可审查 PR、变更不可追溯）。
- 方案：单工具 9 action（status/diff/commit/checkpoint/list/restore/branch/log/pr），替代裸 `code_run` 调 git。对齐 Claude Code 的 git-based checkpoint、Codex 的自动 PR、Cursor 的 diff 预览。
- 实现：
  - `ga.py` 加 `do_git_checkpoint` + 9 个模块级 `git_*` 辅助函数（约 220 行）。`code_search`/`file_find` 旁。
  - `assets/tools_schema.json` + `assets/tools_schema_cn.json` 加 `git_checkpoint` 注册（11 → 12 工具）。
  - `assets/sys_prompt.txt` + `sys_prompt_en.txt` 加「所有 git 操作走 git_checkpoint」段。
  - `mykey_template*.py` 加 `github_token`/`gitlab_token` 可选段（`git_checkpoint action=pr` 用）。
  - `AGENTS.md` 工具表加 git_checkpoint 行 + 注意事项 9「commit/checkpoint 必须在工作分支；restore 必须 no_confirm=true；log 在 .workbuddy/git_restore.log」。
  - `assets/git_checkpoint_smoketest.py` 13 步闭环：clean status → main 拒绝 commit → branch create → untracked 可见 → commit → checkpoint #1 → checkpoint #2 → list 倒序 → log → diff → restore needs_confirm → restore with_confirm → pr 缺 remote 报错 → branch list。
- 关键设计：
  - checkpoint = `git tag -a ga-ckpt-YYYYMMDD-HHMMSSffffff-<shortsha> -m "msg" <sha>`，annotation 存 message。
  - tag 名时间戳到**微秒**（用 `%f`），是为了让 `git tag --sort=-v:refname` 倒序 = 时间倒序。同秒下 git 的 creatordate/taggerdate 排序不稳定。
  - 保护：commit/checkpoint/restore 在 main/master 上被工具硬拒（除非 restore by force）；restore 默认返回 `needs_confirm` 状态，必须传 `no_confirm=true` 才真执行。
  - restore 写 `.workbuddy/git_restore.log` 审计行；返回里带 `previous_head`，reflog 可回退。
  - PR：先 push（选 myfork > origin），再试 `gh pr create`，失败/未装回退 GitHub REST API（`mykey.github_token` / `$GITHUB_TOKEN`），没 token 就返回 compare URL 提示手动建。
- 踩坑：
  - 一开始用 `--sort=-creatordate`，同秒下 git 排序不稳定 → 改用 tag 名 microsec + `-v:refname`。
  - `reset --hard <tag>` 在「目标是当前分支之前 commit」时是**回退当前分支**（不是 detached），`abbrev-ref HEAD` 仍是原分支名。
  - PR 头部保护原写只防 main/master，后发现 detached 状态 (`head=="HEAD"`) 也得防，扩展为 4 元组。

## 为 Bazel 托管项目补齐验证能力（跨语言，优先于原生构建系统）
- 用户问「使用 bazel 管理的项目呢」。
- 设计选择：**不新增独立规则**，而是把「Bazel 优先」分支内联进已有的 Java/C++/Rust 三条规则的 lint 命令最前面 —— 因为 Bazel 是跨语言构建系统，若单独成规则会因扩展名匹配而误拦非 Bazel 的同语言项目。内联分支逻辑：
  1. 从被改文件目录向上走，找 `WORKSPACE`/`MODULE.bazel`（二者任一即 Bazel 工作区根 `w`）。
  2. 若找到 `w`，再从文件目录向上找最近的 `BUILD`/`BUILD.bazel`（package 根 `p`），切到 `w` 跑 `bazel build //<rel>:all`（`rel` = `p` 去掉 `w/` 前缀，根 package 时 rel 置空 → `bazel build //:all`）。
  3. 没找到 `w` → 整段 Bazel 分支空过，原样 fall through 到 Maven/Gradle/CMake/Cargo 原生逻辑。
- **关键安全 guard**：Bazel 分支第一句 `command -v bazel >/dev/null 2>&1 || exit 0` —— 机器没装 bazel 时立即 `exit 0`（干净跳过，耗时 ≤1s）；装了才继续。避免冷启动 `bazel build` 第一次拉依赖/分析超时（已知首构建极慢，60s 不够）或空耗命令查找。
- `assets/sys_prompt.txt` 验证循环段补 Bazel 说明（「优先于 Maven/Gradle/CMake/Cargo」）。
- 验证：shell 探针确认 label 计算正确（`REL=src/com/x` → `//src/com/x:all`）；Maven 回归确认非 Bazel 项目不会被 Bazel 块拦截（`"bazel" not in fbm.lower()`）；C++/Rust 单文件与 Cargo 原生回退仍正常；`have_bazel` 为真时跳过真实 `bazel build`（冷 tempdir 构建会超 60s，逻辑已由 label 探针证明）。三个 JSON 校验通过；`lsp_client.py` 编译通过。
- 环境依赖：Bazel 验证要真跑需用户装 `bazel`（CLI 在 PATH）；缺则干净跳过。Bazel 项目不需要新 LSP 插件 —— 复用已有的 java-lsp/cpp-lsp/rust-lsp（按语言扩展名），设 `GA_PLUGIN_DIRS` 激活。
