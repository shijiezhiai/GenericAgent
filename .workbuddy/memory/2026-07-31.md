## 会话存储 JSON → DuckDB 迁移（实现完成，未上线）

**根因**：`AgentManager._persist()` 每条消息全量重写 `temp/desktop_sessions.json`（含所有会话的 `llm_history`）→ O(N)。实测 150 会话/6000 消息全量同步 **3218ms**，改为单条 append 后 **2.04ms**（~1600x）。

**新增文件**
- `frontends/db_store.py`（355 行）：DBStore 访问层。表 `sessions / messages / conv_folders / projects / raw_logs / log_session_map`。`messages` 独立成表是关键——append 变 INSERT 一行。带"拒绝空覆盖"守卫（对齐 JSON 版防呆）。
- `assets/migrate_to_duckdb.py`（160 行）：一次性导入，行数校验，原文件改名 `.bak`，重跑会 ABORT（幂等守卫），`--force` 重建。

**三种存储模式**（`GA_STORAGE` env，默认 `json` 零行为变更）
- `json`：原逻辑，写 JSON 文件。
- `duckdb`：kernel 进程独占 DB，不再写任何 JSON。
- `replica`：**新增**。legacy bridge 子进程专用，不开 DB、不落盘、不持会话状态。

**关键坑：DuckDB 独占文件锁（血泪）**
- DuckDB 对 .duckdb 文件加**独占锁，第二个进程直接打不开**（已写测试断言验证）。
- 原计划"kernel + legacy bridge 都连同一个 DB"**不可行**。而 legacy bridge 若连不上会静默 fallback 到 json，然后用它那份空/陈旧内存**重写 `desktop_sessions.json`** → 数据损坏。
- 解法：kernel spawn legacy 桥时注入 `GA_STORAGE_SECONDARY=1` → 该进程进入 `replica` 模式，全部持久化路径 early-return。
- **不能禁用 legacy 桥**：`GA_LEGACY_PORT` 在 `desktop_gateway/src/main.rs:29` 默认 14169；`/token-history` **不是**网关显式路由，走 fallback 反代到 legacy 桥。禁掉会白屏用量页。
- 因此 **token 历史保持文件存储**（由 replica 进程服务，必须单一真相源；数据量小非瓶颈）。迁移脚本**不动** `desktop_token_history.json`。待 legacy 桥彻底退役后再入库。

**其它**
- `raw_logs` 补上 `session_id`（`_mirror_raw_log` 传 `sess.id`）；`logid↔session_id` 首次持久化（此前只在内存）。model_responses txt 保留（`/continue` + L4 归档依赖）。
- `bundle_build.py` CORE_DEPS 加 `duckdb`；`.venv` 已装 duckdb 1.5.5。
- 测试脚本 `/tmp/ga_db_suite.py`（CRUD/独占锁/迁移/性能）+ `/tmp/ga_mode_test.py`（三模式落盘行为，需 `.venv` 因为要 aiohttp）。全绿。

**遗留 / 下一步**
- `_load_sessions` 仍一次性把全部消息读进内存（与 JSON 时代相同），启动成本未改善。后续可做懒加载。
- 打包链路（bundle_build + tauri build）尚未验证 duckdb wheel 能否随包分发。

2. `temp/kernel_store.port` 被删 → `ga_config.stop_serving()`(os.remove) 注册在 atexit → **atexit 跑过 = 内核优雅退出，不是崩溃/SIGKILL**。
3. 唯一优雅退出路径：`kernel_server.main()` 的 `for raw in sys.stdin` 收到 **EOF** → break → `finally: _cleanup_legacy()` → `sys.exit(0)`。
4. **级联放大（关键设计缺陷）**：bridge 是 kernel 用 Popen 拉起的子进程，`_cleanup_legacy()`(kernel_server.py:248) 在 kernel 退出时 terminate 它。而 **Skill Hub 的 /api/* 由 bridge(:14169) 服务**（网关 proxy fallback）→ 内核一退出，整个 Web UI 全挂。
5. **不可自愈**：`desktop_gateway/src/kernel.rs:123` reader 循环结束只 `eprintln!("[kernel] stdout closed; kernel process exited")`，**全仓无 restart/respawn/watchdog**；`AppState.kernel: Arc<KernelClient>` 只在 lib.rs:495 spawn 一次。故永久 502。
6. stdin EOF 的上游触发：`KernelClient` 字段声明顺序 `writer_tx` 在前、`_child`(kill_on_drop) 在后 → 一旦 client 被 drop，先关 stdin(→内核 EOF 优雅退出)、后发 SIGKILL，内核有时间跑完 atexit。恰好吻合现象。日志停在一次 `[Output] tokens=6151` 超大输出后（后续 `[Debug] Current context` 都没有），疑与该轮 agent 动作有关（注意 memory 旧坑：禁无条件 pkill python，会杀自己）。

**恢复**：`pkill -f ga-desktop` + `open /Applications/GenericAgent.app`。新进程 56826/56828/56842/56846，port=51585，三接口 200，skills=34、mcp=[filesystem,codegraph]。

**与 DuckDB 迁移无关**：`_cleanup_legacy` 连坐、网关无 watchdog 均为既有逻辑。本次新增的 `ga_config._rpc` 有 `timeout=5` + 异常降级(proxy→transient→json fallback)，内核死亡时独立进程不会挂死；残留 port 文件也能安全降级。

**待修（建议）**：① Rust 网关加 kernel watchdog 自动 respawn（根治，需重编译 Tauri）；② 前端 502 时显示"内核已断开/重启"而非无限加载（零重编译，体验止血）；③ 考虑 bridge 与 kernel 生命周期解耦。与既有待办"给 kernel 加 bridge watchdog"合并推进。
